# Спецификация REST API для интеграции 1С и B2B-платформы (Luxury Optic)

Данный документ описывает требования и формат REST API (JSON) для замены существующего обмена через XML (CommerceML) и FTP.

---

## 1. Архитектурный подход к интеграции

Используется комбинированная **Pull + Push (Webhook)** схема взаимодействия для работы в реальном времени без лишней нагрузки на 1С и сайт:

1. **Каталог (оправы и линзы — полная сверка):**  
   1С публикует HTTP-сервис (REST API), сайт периодически (например, по расписанию раз в несколько часов) запрашивает полный срез каталога (Pull-модель).
2. **Точечное обновление остатков и цен в реал-тайме (Webhook от 1С -> Сайт):**  
   При проведении заказа, продаже, оприходовании или списании в 1С — 1С отправляет `POST`-запрос на вебхук сайта (`POST /api/v1/webhooks/1c/stocks/`) со списком только тех товаров (`id_1c`), по которым изменился остаток или цена. Это избавляет от необходимости делать тяжёлый полный `GET`-запрос всего каталога после каждого заказа.
3. **Контрагенты (Webhook от 1С -> Сайт + резервный Pull):**  
   * **Реал-тайм (основной):** при создании или изменении контрагента в 1С, 1С сразу отправляет вебхук на сайт (`POST /api/v1/webhooks/1c/customers/`), чтобы клиент моментально появился в системе.
   * **Периодическая сверка (резервный):** сайт может периодически опрашивать `GET /api/v1/customers` на стороне 1С для фоновой синхронизации.
4. **Заказы и контроль остатков (Push от Сайта -> 1С):**  
   * Сайт контролирует остатки на каждом шаге: не даёт добавить в корзину или оформить заказ, если `stock <= 0` или запрошенное количество превышает остаток в БД сайта.
   * В момент оформления заказа сайт синхронно отправляет `POST /api/v1/orders` в 1С.
   * 1С проверяет фактический остаток, резервирует товар, создаёт документ и возвращает номер заказа в 1С + обновлённые остатки по позициям заказа. Если в 1С товара уже не хватает, 1С возвращает ошибку `422 PRODUCT_OUT_OF_STOCK` с актуальными остатками, а сайт сразу обновляет их у себя и сообщает клиенту.

### Общие требования:
* **Формат данных:** `JSON`, кодировка `UTF-8`.
* **Авторизация (двусторонняя):** Bearer Token в заголовке (`Authorization: Bearer <token>`) или Basic Auth (`Authorization: Basic <base64>`), как при запросах Сайт -> 1С, так и при вебхуках 1С -> Сайт.
* **Даты:** ISO 8601 (`YYYY-MM-DDTHH:MM:SS`).
* **Числа и цены:** Цены и размеры — строками или числами с фиксированной точкой (напр. `"450000.00"`), валюта — `UZS`. Остатки — целые числа (`>= 0`).

## 4. Контрагенты и Пользователи (B2B-клиенты)

Для того чтобы новые оптовые клиенты из 1С сразу получали доступ к сайту и Telegram-боту (не дожидаясь планового опроса), используется **реал-тайм вебхук от 1С к сайту**, дополненный периодическим `GET`-запросом для полной сверки.

### 4.1. Вебхук от 1С при создании/изменении контрагента (Реал-тайм)
**Направление:** `1С -> Сайт`  
**Метод на стороне сайта:** `POST /api/v1/webhooks/1c/customers/`  
*(Вызывается 1С автоматически при записи нового контрагента или изменении его контактных данных).*

#### Тело запроса от 1С к сайту (JSON):
*(Поддерживается передача как одного объекта, так и списка в массиве `items`)*
```json
{
  "items": [
    {
      "id_1c": "7ea8102b-11c2-4a01-99ee-ab012845c110",
      "company_name": "ООО «Optic Grand Tashkent»",
      "inn": "123456789",
      "is_active": true,
      "contact_person": {
        "full_name": "Азизов Азиз Азизович",
        "first_name": "Азиз",
        "last_name": "Азизов",
        "phone": "+998901234567",
        "email": "aziz@opticgrand.uz"
      }
    }
  ]
}
```

#### Ответ сайта (HTTP 200 OK):
```json
{
  "status": "success",
  "processed": 1,
  "results": [
    {
      "id_1c": "7ea8102b-11c2-4a01-99ee-ab012845c110",
      "company_id_site": 12,
      "user_id_site": 15,
      "telegram_link_token": "c4f1d2e3-88a1-4b2c-9f00-112233445566"
    }
  ]
}
```

### 4.2. Периодическая сверка контрагентов (Резервный Pull)
**Направление:** `Сайт -> 1С`  
**Метод на стороне 1С:** `GET /api/v1/customers`  
Возвращает полный список активных контрагентов в том же формате `{"items": [...]}` для фоновой синхронизации.

#### Назначение полей контрагента:
| Поле | Тип | Обязательное | Описание |
| :--- | :--- | :---: | :--- |
| `id_1c` | string (UUID) | Да | GUID контрагента в 1С |
| `company_name` | string | Да | Юридическое / торговое наименование компании |
| `inn` | string | Нет | ИНН компании (для исключения дубликатов) |
| `is_active` | boolean | Нет | Статус активности клиента (по умолчанию `true`) |
| `contact_person.phone` | string | Да | Номер телефона (используется как логин на сайте) |
| `contact_person.email` | string | Нет | Email для уведомлений и сброса паролей |
| `contact_person.first_name`| string | Да | Имя контактного лица |
| `contact_person.last_name` | string | Нет | Фамилия контактного лица |
| `contact_person.full_name` | string | Нет | Полное ФИО контактного лица |

## 5. Выгрузка заказов в 1С и защита от заказа при нулевых остатках

### Логика защиты от заказов без остатка:
1. **На стороне сайта (до отправки в 1С):**
   * В каталоге отображаются только товары с `stock > 0`.
   * При добавлении в корзину (`POST /api/v1/orders/cart/add/`) и изменении количества (`PATCH`) сайт проверяет, что `quantity <= product.stock`.
   * При нажатии «Оформить заказ» (`POST /api/v1/orders/checkout/`) сайт повторно проверяет остатки всех позиций корзины в транзакции.
2. **В момент оформления заказа (`Сайт -> 1С`):**
   * Сайт отправляет `POST /api/v1/orders` в 1С.
   * **Если остатков в 1С достаточно:** 1С проводит/резервирует заказ и в ответе (либо отдельным вебхуком п. 6) возвращает новые остатки по купленным товарам. Сайт сразу обновляет `stock` у себя в БД без полного `GET`-запроса каталога.
   * **Если за секунду до этого товар купили в 1С и остатка не хватает:** 1С возвращает `HTTP 422` (`PRODUCT_OUT_OF_STOCK`) и список актуальных остатков по проблемным позициям (`items_stock`). Сайт мгновенно обновляет эти остатки у себя, не оформляет заказ и выводит клиенту точное сообщение, какого товара и сколько реально осталось.

### Метод на стороне 1С: `POST /api/v1/orders`
**Направление:** `Сайт -> 1С`

## 6. Вебхук от 1С: Точечное обновление остатков и цен в реал-тайме

Чтобы не нагружать 1С и сайт полным `GET`-запросом всего каталога при каждом движении товара, 1С при создании/проведении заказа, реализации, возврате или оприходовании отправляет на сайт лёгкий POST-запрос только с изменившимися товарами.

**Направление:** `1С -> Сайт`  
**Метод на стороне сайта:** `POST /api/v1/webhooks/1c/stocks/`

#### Тело запроса от 1С к сайту (JSON):
```json
{
  "reason": "order_created",
  "items": [
    {
      "id_1c": "1dc92560-58c0-11f0-b0e4-ee81ce5b1c14",
      "stock": 12,
      "price": 420000.00
    },
    {
      "id_1c": "3c84636c-099c-11f0-96ec-d85ed3a775a0#e3e35f25-9dcc-11e5-8146-001e676d277d",
      "stock": 0
    }
  ]
}
```
*(Поле `price` опционально: если передано только `stock`, обновляется только остаток. Если `stock` стал `0`, товар моментально скрывается с витрины и блокируется для заказа).*

#### Ответ сайта (HTTP 200 OK):
```json
{
  "status": "success",
  "updated_frames": 1,
  "updated_lenses": 1,
  "not_found": []
}
```

## 7. Что выигрывает проект при переходе на эту схему?

1. **Мгновенная регистрация клиентов:** Новый контрагент из 1С прилетает вебхуком (`POST /api/v1/webhooks/1c/customers/`) за долю секунды и сразу может авторизоваться.
2. **Актуальные остатки без перегрузки сети:** После любого заказа или продажи в 1С вебхук `POST /api/v1/webhooks/1c/stocks/` точечно обновляет остатки конкретных позиций за миллисекунды, не скачивая тысячи товаров целиком.
3. **Гарантия отсутствия заказов «в минус»:** Двойная проверка остатков (на сайте при работе с корзиной + в 1С в момент оформления с возвратом `updated_stocks`) полностью исключает заказ закончившегося товара.
4. **Точные оптические параметры:** Отказ от регулярных выражений парсинга SPH/CYL/DIA исключает человеческий фактор при опечатках в названиях линз в 1С.
5. **Безопасность:** Отказ от небезопасного FTP-протокола в пользу защищенного HTTPS с авторизацией по токену.
